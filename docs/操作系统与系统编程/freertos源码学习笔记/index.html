FreeRTOS源码实现与API#

FreeRTOS前置基础知识#

裸机系统和多任务系统#

裸机系统#

裸机系统分为轮询系统和前后台系统

轮询系统#

轮询系统只适合顺序执行的程序，主程序在while死循环里一直跑，没有区分事件的响应和处理，可能导致事件未响应丢失，当遇到需要实时性的功能时难以及时响应

前后台系统#

比起轮询系统多了中断响应，但处理事件的方式依然是按顺序执行 前后台系统通过中断响应置事件标志位，事件处理细节交给主程序完成 能把事件的响应和处理分开，确保事件不会丢失，中断能嵌套，大大提升了程序实时响应能力

多任务系统#

  • 由操作系统控制多任务同时执行，多任务系统的事件响应也是在中断里执行的，但事件的处理是在任务中完成的，在多任务系统中，任务和中断一样具有优先级，优先级高的任务会被优先执行，进一步提高了系统实时性。
  • 每个任务是独立，互不干扰的，具有优先级。通过操作系统调度管理，方便各个任务的隔离处理，但操作系统也占用了额外FLASH和RAM开销。
  • 单核处理器可以通过系统快速切换多任务执行来造成多任务并行的假象。

任务调度#

Freertos使用固定优先级的抢占式调度，对于同优先级的任务使用时间片轮询调度。

  • 抢占式调度：允许高优先级的任务在任何时刻抢占低优先级的任务，保证高优先级任务的实时响应，优先级数值越大优先级越高。
  • 时间片轮询调度：对于同优先级的任务，CPU为每个任务分配相同时间片，公平分配每个任务获得CPU的时间。

任务状态#

FreeRTOS中一共有四种任务状态： 1. 运行态：当任务正在使用CPU时就叫做运行态，单核处理器同一时间只能有一个任务处于运行态。 2. 就绪态：能够执行但因为同等或更高优先级的不同任务已经处于运行态而等待的任务 3. 阻塞态：任务当前在等待延时或外部事件。 4. 挂起态：类似暂停，调用函数来进入或解除挂起态。 只有就绪态才能变成运行态。这四种状态，除了运行态，其他三种状态都有对应的任务列表：

  • 就绪列表：pxReadyTasksLists[x],x代表任务优先级,有几个优先级就有几个列表
  • 阻塞列表：pxDelayedTaskList
  • 挂起列表：xSuspendedTaskList

FreeRTOS滴答时钟#

FreeRTOS通过Systick计数中断来增加滴答数，每次滴答数增加时，实时内核必须检查当前是否是解除阻塞或唤醒任务的时间

上下文切换#

任务运行时用到的全部寄存器：R0-R15、xPSR、LR等，就是任务上下文。每个独立任务都有自己一套上下文，保存在任务栈(PSP)中。

上下文切换本质：暂停当前正在执行的任务，，把它的所有寄存器存入自己的任务栈中，挑选另一个高优先级的任务，从它的栈里恢复所有寄存器。

PSP 是线程堆栈指针，任务执行时 PSP 指向当前任务栈栈顶。触发 PendSV 进入 Handler 模式时，CPU 先借助 PSP 把 8 个寄存器压入旧任务栈，随后 CPU 切换活跃 SP 为 MSP 运行中断代码；在 PendSV 内手动保存剩余寄存器，并把最终 PSP 存入旧任务 TCB。调度选中新任务后，从新任务 TCB 读取栈地址恢复到 PSP，手动恢复 R4~R11；退出异常时硬件自动弹出剩余寄存器，完成切换。

触发异常进入Handler模式后，LR 不再是普通函数返回地址，CPU自动载入一段特殊编码0xFFFFFFF9/0xFFFFFFFD，这个值告诉 CPU：退出异常后切回线程模式、使用 PSP。

PendSV异常抢占优先级要设置成最低优先级，避免任务切换抢占其他异常和中断导致错误。

FreeRTOS数据类型和命名规范#

数据类型#

1.TickType_t，可以是16位或32位的变量类型，由configUSE_16_BIT_TICKS配置，0为32位，1为16位。此类型变量通常用来表示系统节拍计数器的值。滴答定时器每定时中断一次加一

2.BaseType_t，架构的类型，在32位架构上为32位，16位架构上为16位

3.StackType_t用于存储堆栈项目的类型。通常是16位架构上的16位类型；32位架构的32位类型，供FreeRTOS内部使用

变量类型#

1.uint32_t类型变量以ul为前缀，‘u’表示unsigned，’l’表示long 2.uint16_t类型变量以us为前缀，‘u’表示unsigned，’s’表示short 3.uint8_t类型变量以uc为前缀，‘u’表示unsigned，‘c’表示char 4.非stdint类型的变量以x为前缀。例如BaseType_t和TickType_t。 5.size_t变量类型也带有x前缀 6.枚举变量以e为前缀 7.指针以附加p为前缀

函数类型#

1.静态函数(static)以prv为前缀 2.API函数的前缀为其返回类型，void返回类型函数前缀为v 3.API函数名称以定义API函数的文件名称开头

宏类型#

1.宏具有明确的描述性，并使用完整的单词 2.宏以定义宏的文件为前缀，前缀为小写 3.除前缀外，所有宏均使用大写字母书写，并用下划线分隔单词

汇编基础#

汇编指令#

读取LOAD：LDR R0, [Addr A] (CPU从RAM地址A读取数据并存放在R0寄存器)

  • LDR:读4个字节
  • LDRH：读2个字节
  • LDRB： 读1个字节

写入Store：STR R0, [Addr A] (CPU把R0的值写入到RAM地址A位置)

加法ADD：ADD R0,R1,R2(把R1+R2的值存放到R0寄存器中)

压栈Push：Push{R3,LR},把LR和R3寄存器的值压到SP指针指向的位置，入栈顺序固定为高位寄存器为高地址，低位寄存器为低地址，SP指针每压入一个数据自动指向下一个位置 出栈Pop：POP{R3，PC}，读内存，把SP当前内存值给R3，SP上移，把当前内存值赋给PC

AAPCS 调用约定#

1.r0‑r3：caller‑saved 调用者保存，用来传前 4 个参数 2.r4‑r11：callee‑saved 被调用者保存，函数只要碰必须 PUSH/POP 恢复 3.BL 指令自动填 LR 为下一条指令地址；嵌套调用 LR 会被覆盖，需要压栈保存 LR

Cortex-M中断硬件栈帧#

1.进中断硬件自动压 8 个寄存器：xPSR PC LR R12 R3 R2 R1 R0，压到当前正在运行的 SP上 2.硬件不会保存 R4‑R11，软件手动保存 3.中断返回：BX EXC_RETURN，硬件自动弹出这 8 个寄存器恢复现场。

Thumb-2 核心指令#

LDR / STR 内存读写，寄存器 ↔ RAM/Flash LDMIA / STMDB 批量加载 / 存储，保存恢复 R4‑R11 上下文关键指令 PUSH / POP 栈操作，满递减栈 BL / BX 函数跳转、返回；BX 可以跳寄存器（LR） MRS / MSR 读写特殊内核寄存器：PSP、MSP、CONTROL、BASEPRI CPSID I / CPSIE I 关开总中断 DSB / ISB 内存同步屏障

内核寄存器#

  • R0‑R15：通用寄存器，PC (R15)、LR (R14)、SP (R13)
  • MSP / PSP 双栈指针：异常用 MSP，任务线程模式用 PSP，CONTROL 寄存器 bit0 切换栈指针
  • APSR 状态标志：Z/N；S后缀指令（MOVS ADDS SUBS）会更新标志，不带 S 不更新
  • EXC_RETURN 魔法 LR 值：中断返回魔数，BX LR触发硬件恢复栈帧，区分用 MSP 还是 PSP 出栈

CPU与RAM和Flash#

对于一段程序代码，变量存放在RAM中，Flash存放着汇编指令，控制CPU读写RAM或者处理数据。CPU把RAM中的变量值拿出来，存放在CPU的R0-R15寄存器中，并在CPU完成对应变量的操作，如加减乘除，最后根据指令把结果放回RAM中

CPU的寄存器#

寄存器4字节，R0-R12数据寄存器，R13:SP(栈指针), R14:LR(返回地址), R15:PC(当前指令地址)

保存现场#

当在函数内部调用子函数、产生中断/异常或RTOS任务切换时需要保存CPU内的寄存器值称为保存现场

  • 普通函数调用：R0-R3、R12由主函数负责选择是否PUSH保存数据在子函数调用完后POP；R4-R11、LR，子函数在开头PUSH，返回时POP

  • 中断触发时，硬件自动往栈里压入R0-R3、R12、LR、PC、xPSR；R4-R11如果被使用则由软件手动PUSH/POP

  • RTOS任务切换：每个任务有自己独立的栈，发生任务切换时，RTOS软件手动把全部寄存器保存到该任务自己的栈，回来时再从自己的栈把全部寄存器恢复。

FreeRTOS中断管理#

STM32的中断优先级是由中断优先级配置寄存器高4位配置的，支持最多16位中断优先级，数值越小优先级越高(FreeRTOS任务调度的任务优先级数值越大优先级越高)

FreeRTOS将PendSV和SysTick设置最低优先级(数值最大，15)，保证系统任务切换不会阻塞系统其他中断的响应

FreeRTOS利用BASEPRI寄存器实现中断管理，屏蔽优先级低于某一个阈值的中断。比如：BASEPRI设置为0x50(高四位有效)，代表中断优先级在5-15内均被屏蔽，0-4中断优先级正常执行

在中断服务函数里调用FreeRTOS的API函数时：

  • 中断服务函数的优先级需在FreeRTOS所管理的范围内，阈值由configMAX_SYSCALL_INTERRUPT_PRIORITY指定
  • 所有优先级设置为抢占优先级，方便FreeRTOS管理
  • 中断服务函数里调用的API函数必须带有FromISR后缀

FreeRTOS开关中断#

FreeRTOS开关中断函数是宏定义，在portmacro.h中：

  • #define portDISABLE_INTERRUPTS()                  vPortRaiseBASEPRI() //配置BASEPRI
  • #define portENABLE_INTERRUPTS()                   vPortSetBASEPRI( 0 ) //不屏蔽中断

/*3. 中断嵌套行为相关配置 cm3内核:我们要求4个优先级位全部为抢占优先级位

底层链表源码实现#

FreeRTOS中与链表相关的操作均在list.h和list.c这两个文件中实现。这里的链表是双向循环链表，初始时有固定头尾相连的哨兵节点，并用索引index存要读的下一个节点，而index上一个节点则为该链表实际的尾部。

链表项类型#

一个链表项结构体里有5个成员，分别实现：

  • 辅助节点排序优先级计数，值越小，优先级越高
  • 指向前一个、后一个链表项
  • 指向该链表项所在的TCB结构体
  • 指向链表项链表

链表项初始化#

链表项初始化时只要把pvContainer置NULL表示该节点未插入链表

链表根节点类型#

一个链表根节点有3个成员，分别实现：

  • 记录链表中链表项个数
  • 记录指向下一个节点的索引游标
  • 存放永远为链表末尾的哨兵节点

链表根节点初始化#

任务的创建删除与源码实现#

在裸机系统中，局部变量、函数调用和返回保存现场都被放在栈中，这个栈由启动文件分配大小。而在RTOS中，每个任务都是独立的，需要为每个任务分配独立的栈空间，这个栈可以是预先定义好的全局数组，也可以是动态分配的一段内存空间

任务可以是动态或静态创建的。 动态创建时，任务控制块和栈大小都动态分配，任务删除时内存可以释放。 静态创建时，任务控制块和栈大小都要定义全局数组，任务删除时内存不能释放。

TCB结构体类型#

在裸机系统中，程度由CPU顺序执行。而在RTOS中，任务执行由系统调度，为每个任务分配一个任务控制块(TCB)，系统对任务的所有操作通过任务控制块完成。

TCB结构体内部成员包括：

  • 任务栈顶指针
  • 任务状态/事件节点
  • 任务优先级
  • 任务栈指针
  • 任务名字

为栈和TCB分配内存，并完成TCB初始化，在栈中伪造中断栈帧并把TCB挂到对应优先级的就绪列表

栈初始化函数#

当PendSV异常发生时，硬件会自动把任务A的R0、R1、R2、R3、R12、R14、R15(PC)和xPSR这8个寄存器压入栈中，随后在PendSV_Handler中把PSP指针指向任务B，当退出PendSV异常时，硬件自动把任务B的栈中寄存器值弹出，完成上下文切换。

  • R0、R1、R2、R3：称为参数寄存器，用于存放函数的参数，局部变量和临时计算结果。
  • R12：内部过程调用寄存器(IP)，作为函数跳转时的临时中转
  • R14:链接寄存器(LR)，保存函数的返回地址
  • R15：程序计数器(PC)，指向CPU下一条要执行的指令地址，对于新任务，PC填入了任务函数的入口地址
  • xPSR：程序状态寄存器，保存当前的处理器模式和运算标志位

消息队列相关函数与源码实现#

消息队列能在任务与任务间、中断和任务间传递不固定长度的消息。发送消息可以是先进先出(FIFO)，也可以是后进先出(LIFO)，具体看发送API。

  • 当队列中消息满时，如果发送任务设置了超时时间，则把发送任务切换成阻塞态，在有空位或超时时间到时唤醒
  • 当队列中消息空时，如果读取任务设置了超时时间，则把读取任务切换成阻塞态，在有空位或超时时间到时唤醒

互斥量相关函数与源码实现#

互斥信号量是包含优先级继承机制的二进制信号量。优先级继承是为了解决优先级翻转而设计的机制，当一个高优先级任务等待一个低优先级任务所持有的资源时，系统会提升低优先级任务的优先级，避免高优先级任务长时间等待

优先级翻转#

在一个多任务环境中，一个较低优先级的任务阻塞了一个较高优先级任务的执行，导致高优先级任务无法及时完成。

互斥量相关函数#

  • 优先级继承无法完全解决优先级翻转
  • 互斥信号量不能在中断中使用

内存管理的源码实现#

FreeRTOS操作系统将内核与内存管理分开实现，并提供了多种内存分配算法的实现API而不是使用C标准库中的malloc，因为设计使用场景不合适。

在实时系统中，系统对于内存分配时间要求较为苛刻，分配内存的时间必须是确定的，并且一般不用虚拟内存管理。

内存可以是静态分配也可以是动态分配，一些可靠性要求高的系统应使用静态分配，但内存使用效率低。而动态分配可提高内存的使用效率。

heap4算法源码实现#

heap4内存分配使用的是首次匹配算法，通过单链表把所有空闲块连起来，并用遍历找到第一个空闲块大小符合的块用来分配。链表中的空闲块是以地址从低到高的顺序排序的，并且有新空闲块插入链表时如果两边有相邻地址的空闲块，还会把它们合并。

事件相关函数及源码实现#

事件标志组：按位管理事件，一个变量的每一位代表一个事情是否发生 0-23位是事件组，24到26位为控制位。27到31位为未使用位。

(API)xEventGroupSetBits#

功能：把一个或多个事件位置 1，并唤醒所有等待条件因此满足的任务。

返回值：

  • EventBits_t，设置后的事件位当前值（可能被唤醒任务清除过部分位）。

功能：清除事件组中的一个或多个事件位。将指定的位清零，其余位保持不变。

返回值：

  • EventBits_t，返回的是清除操作之前的事件位图。

EventBits_t uxOldBits = xEventGroupClearBits( xEventGroup, BIT_A);

    // 说明清除前 BIT_A 是置位状态
}

(API)xEventGroupWaitBits#

功能：等待事件组中的一个或多个事件位。支持“等任意事件”或“等全部事件”，可选择满足后自动清除。条件不满足时任务进入阻塞态。

返回值：

  • EventBits_t，条件满足或超时时的当前事件位图。
  • 如果事件组被删除，返回 0。

- xClearOnExit        满足后是否自动清除这些    pdTRUE / pdFALSE
- xWaitForAllBits     等全部还是等任意          pdTRUE（全部）/ pdFALSE（任意）
- xTicksToWait        超时时间                  portMAX_DELAY 表示死等

(API)xTaskNotify#

功能：向指定任务发送通知，并指定更新通知值的方式（eNotifyAction）。

返回值：

  • pdPASS（发送成功）
  • pdFAIL（仅当 eAction == eSetValueWithoutOverwrite 且上次通知未读走时返回）。

configUSE_TASK_NOTIFICATIONS 1

// 模拟二值信号量（只通知，不传值）
xTaskNotify( xTaskToNotify, 0, eNoAction );

// 模拟事件组（按位设置）
#define BIT_X  (1 << 0)
#define BIT_Y  (1 << 1)
xTaskNotify( xTaskToNotify, BIT_X | BIT_Y, eSetBits );

// 模拟计数信号量（加一）
xTaskNotifyGive( xTaskToNotify );  // 等价于 xTaskNotify( xTask, 0, eIncrement )

// 传递一个数值（覆盖写）
xTaskNotify( xTaskToNotify, 12345, eSetValueWithOverwrite );

// 传递关键数据（不覆盖，需检查返回值）
if( xTaskNotify( xTaskToNotify, sensor_value, eSetValueWithoutOverwrite ) == pdFAIL )
{
    // 上次的值还没被读走，本次发送失败
}

(API)xTaskNotifyWait#

功能：阻塞等待任务通知，可选择在进入和退出时清除通知值的指定位。收到通知后读走值。

返回值：

  • pdTRUE（收到通知）
  • pdFALSE（超时未收到）

configUSE_TASK_NOTIFICATIONS 1

// 等任意事件，收到后读值
uint32_t ulValue;
if( xTaskNotifyWait( 0, 0, &ulValue, portMAX_DELAY ) == pdTRUE )
{
    // 收到通知，ulValue 里是值
}

// 进入前清所有位，退出后清所有位
xTaskNotifyWait( 0xFFFFFFFF, 0xFFFFFFFF, &ulValue, portMAX_DELAY );

// 只关心有没有通知，不关心值
if( xTaskNotifyWait( 0, 0, NULL, portMAX_DELAY ) == pdTRUE )
{
    // 有事件发生
}

// 非阻塞查询
if( xTaskNotifyWait( 0, 0, &ulValue, 0 ) == pdTRUE )
{
    // 已经有通知，立刻处理
}

(API)ulTaskNotifyTake#

功能：阻塞等待任务通知，并把通知值清零或减一。专门用于模拟二值信号量或计数信号量的 Take 操作。

返回值：

  • uint32_t，返回取走之前的通知值
  • 返回 0 表示超时未收到。

configUSE_TASK_NOTIFICATIONS 1

// 模拟二值信号量
uint32_t ulCount = ulTaskNotifyTake( pdTRUE, portMAX_DELAY );
if( ulCount > 0 )
{
    // 收到信号，处理
}

// 模拟计数信号量
uint32_t ulCount = ulTaskNotifyTake( pdFALSE, portMAX_DELAY );

(API)xTaskNotifyGive#

功能：向指定任务发送通知，通知值 +1，固定使用 eIncrement 动作。用于模拟计数信号量的 Give 操作。

返回值：pdPASS（总是成功）

configUSE_TASK_NOTIFICATIONS 1

// 接收通知（模拟二值信号量）
ulTaskNotifyTake( pdTRUE, portMAX_DELAY );   // 取走清零

// 接收通知（模拟计数信号量）
ulTaskNotifyTake( pdFALSE, portMAX_DELAY );  // 取走减一

(API)xTaskNotifyAndQuery#

功能：向指定任务发送通知，同时输出更新前的旧通知值。与 xTaskNotify 的唯一区别是多了一个输出参数 pulPreviousNotifyValue。

返回值：

  • pdPASS（发送成功）。
  • pdFAIL（仅当 eAction == eSetValueWithoutOverwrite 且上次未读走时）。

configUSE_TASK_NOTIFICATIONS 1

uint32_t ulOldValue;
xTaskNotifyAndQuery( xTaskHandle, 0x1234, eSetValueWithOverwrite, &ulOldValue );
